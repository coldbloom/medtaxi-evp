# Заявки, телефонные клики и собственная аналитика

Браузер → Nginx `/api/` → `conditioners-server` → транзакция SQLite
(событие/заявка и необходимые задания уведомлений) → HTTP-подтверждение браузеру.
Фоновый обработчик независимо отправляет уведомления в Telegram и VK.
Работа каналов и их повторные попытки не задерживают приём заявки.

Эта схема относится к Medtaxi. Остальные сайты, использующие `conditioners-server`,
сохраняют свои прежние обработчики. Backend определяет Medtaxi по настроенному
`MEDTAXI_URL`, явно добавленным `MEDTAXI_ADDITIONAL_ORIGINS` и Origin запроса.
Для резервного домена нужен отдельный `/api/` proxy; оба адреса сохраняются в одной
Medtaxi DB с фактическим Origin. Origin ограничивает браузерные источники, но не является
секретом или защитой от произвольного HTTP-клиента.

## Контракт и подтверждение записи

| Действие | Endpoint | Подтверждение |
| --- | --- | --- |
| Нажатие `tel:` | `POST /api/call-clicks` | `202`, `accepted: true`, совпадающий `eventId` |
| Просмотр страницы, открытие формы, ответ о звонке | `POST /api/v1/medtaxi/events` | `202`, `accepted: true`, совпадающий `eventId` |
| Обратный звонок | `POST /api/feedback` | `200`, `success: true`, совпадающий `requestId`, непустой `leadId` |

Успех означает, что данные записаны в БД. Он не подтверждает состоявшийся звонок,
доставку уведомления оператору или прочтение сообщения. При ошибке записи backend
возвращает ошибку; frontend не показывает «Заявка принята».

Формы/клики сохраняют прежние пути. **Новый backend нужно развернуть до нового frontend**:
форма теперь проверяет тело подтверждения, а не только HTTP 2xx. HTML от прокси,
пустой ответ или чужой `requestId` не считаются успешной отправкой.

## Телефонные ссылки

```tsx
import { TrackedPhoneLink } from "@/app/components/tracking/TrackedPhoneLink";

<TrackedPhoneLink phone="+79895052785" trackingId="hero" className="button">
  Позвонить
</TrackedPhoneLink>
```

`phone` — номер службы без пробелов/скобок, `trackingId` — постоянное имя расположения
в snake_case. Сочетание `page` + `trackingId` определяет кнопку. Ссылка остаётся
обычным серверным `<a href="tel:...">`; атрибуты доступности передаются без изменений.
`PhoneClickTracking` в корневом layout использует один capture-listener, включая
позднее появившиеся ссылки в модальных окнах. Неразмеченная ссылка получает
`trackingId: "unlabelled"`. На `/donetsk` сохраняются также цели Яндекс Метрики.

На каждый клик создаётся новый UUID. `phoneClickIdentity` через WeakMap связывает
его с исходным DOM-событием: listener аналитики и listener опроса получают один
ID независимо от порядка выполнения. `tel:` не отменяется и не ожидает HTTP-ответ.
До hydration и без JavaScript ссылка работает, но собственные события не собираются.

Пример payload клика:

```json
{
  "eventId": "8039e6de-b47c-4c6e-8507-b128e1739e6c",
  "sessionId": "8ff232a0-66fc-4ee0-bcad-64c2b8614452",
  "trackingId": "hero",
  "phone": "+79895052785",
  "page": "/donetsk",
  "utm": { "source": "yandex", "campaign": "donetsk" },
  "yclid": "1234567890",
  "referrer": "https://yandex.ru/search/",
  "clientTimestamp": "2026-11-03T12:34:00.000Z"
}
```

## Посещения, сессия и повторная доставка

`trackingSession` сохраняет UUID сессии и первоначальные UTM/yclid/referrer
в `sessionStorage.medtax_call_session_v1`. Переход между страницами не перезаписывает
первый источник. Referrer сохраняется без query, fragment и credentials; `page` —
без query/hash. Сессия вкладки не является достоверным идентификатором человека:
дублирование вкладки может скопировать sessionStorage. Fingerprinting не используется.

`MetrikaPageViews` наблюдает завершённые переходы Next.js и отправляет собственное
`page_view` независимо от доступности Яндекс Метрики. Повторный effect в Strict Mode
не создаёт лишний просмотр; переход назад/вперёд на другую страницу учитывается.
Типы общего endpoint: `page_view`, `callback_open`, `call_outcome`. Контекст включает
`eventId`, `sessionId`, `page`, `clientTimestamp` и применимые метки источника/кнопки.
Просмотры, открытие формы и ответ «дозвонился» сохраняются для аналитики без отдельного
мгновенного уведомления. Клик по телефону, ответ «не дозвонился» и отправленная заявка
создают задания для Telegram и VK; сводки посещений готовит backend.

`analyticsQueue` хранит только разрешённые поля событий, а не имя, контактный номер
посетителя или комментарий формы. Поле `phone` в событиях — набранный номер службы.
Очередь находится в `sessionStorage.medtax_analytics_queue_v1`:

- максимум 100 событий на вкладку, срок жизни 24 часа; при переполнении удаляются старые;
- максимум 2 параллельных запроса, таймаут каждого 8 секунд;
- экспоненциальная задержка с jitter до 5 минут, учёт серверного `Retry-After`;
- восстановление после reload и повтор при событии `online`;
- повтор сохраняет исходный payload/UUID, backend дедуплицирует его;
- запись удаляется после корректного подтверждения или постоянного отказа
  `400/403/409/413`; истечение срока/лимит также ограничивают хранение.

JSON отправляется как `text/plain;charset=UTF-8` с `fetch keepalive`, чтобы не требовать
CORS preflight для аналитики. `keepalive` не гарантирует доставку при закрытии браузера.
Если storage запрещён, сессия и очередь работают только в памяти страницы. До приёма
backend события могут потеряться; после закрытия вкладки sessionStorage не является
постоянным архивом. Серверная SQLite-очередь решает другую задачу — сохранение и
повторную доставку уже принятых событий при перезапусках backend и сбоях TG/VK.

## Опрос после звонка и форма

`CallFeedback` показывает вопрос «Удалось ли вам дозвониться к нам?» после возвращения
из приложения звонков: через 800 мс при видимом окне с фокусом. Если сайт всё время
остаётся активным, используется задержка 15 секунд. Новый клик заменяет ожидающий
опрос. Закрытие вкладки/reload сбрасывает ожидание.

Браузер не определяет результат разговора автоматически. Только явный ответ посетителя
создаёт `call_outcome` с `outcome: "connected"` или `"not_connected"` и
`sourceEventId` исходного клика. «Да» показывает благодарность. «Нет» сразу фиксирует
ответ, затем открывает короткую форму имени/телефона/согласия. Сам ответ ещё не является
контактной заявкой, если пользователь не отправил форму.

`useCallbackRequest` отправляет данные в `/api/feedback`:

- имя, телефон, комментарий и подтверждение согласия с версией и временем;
- `kind: "callback"` либо `"missed_call_followup"`;
- `requestId`, текущую сессию, путь страницы, CTA и первоначальный источник;
- `sourceEventId`, когда заявка продолжает попытку звонка.

Для одного содержимого формы повтор после сетевой ошибки использует **тот же requestId
и тот же consentedAt**. Если данные изменены, создаётся новый requestId. Backend
возвращает прежнюю заявку при точном повторе и `409`, если ID использован с другим
содержимым. Заявки не объединяются автоматически только по номеру телефона.

«Заявка принята!» появляется после корректного подтверждения записи. При ошибке
или таймауте 15 секунд черновик остаётся в памяти компонента для ручного повтора.
При reload черновик теряется; имя/телефон/комментарий не записываются в очередь
аналитики и не отправляются автоматически в фоне. Активная отправка защищена от
закрытия и повторного нажатия. При размонтировании запрос отменяется; сервер уже мог
успеть записать его. Стабильный ID защищает повтор из сохранившегося черновика;
после полного размонтирования/reload новый экземпляр формы не восстанавливает старый ID.

Компоненты сохраняют прежнее разделение: `ContactModal` управляет шагами,
`ContactDialog` — фокусом/клавиатурой/прокруткой, `CallbackForm` — полями,
`useCallbackRequest` — жизненным циклом HTTP-запроса. `LazyContactModal` загружает
диалог при необходимости. Страницы и SEO остаются Server Components.

## Локальная отладка без production-уведомлений

Используйте отдельную локальную БД и тестовые получатели; не копируйте рабочие токены
и chat/peer ID в тестовое окружение. Без настроенных провайдеров backend всё равно
сохраняет принятые заявки, но доставка ожидает настройки канала.

1. В локальном `conditioners-server` задать `HOST=127.0.0.1`, `PORT=3235`,
   `MEDTAXI_URL=http://localhost:3079`. `MEDTAXI_URL` должен точно совпадать с origin
   страницы в браузере, включая порт. Запустить `npm run dev` по README backend.
2. В frontend `.env.local` задать:

   ```dotenv
   NEXT_PUBLIC_API_URL=http://localhost:3235/api
   ```

3. Запустить `yarn dev --port 3079`, открыть `http://localhost:3079/donetsk`.
   Не заменять `localhost` на `127.0.0.1`, не изменив соответствующий Origin backend.
4. В DevTools → Network включить Preserve log, проверить `call-clicks`,
   `v1/medtaxi/events`, `feedback`. У формы должен вернуться совпадающий `requestId`
   и непустой `leadId`; событию — совпадающий `eventId` и `accepted: true`.
5. Отключить сеть, создать событие, восстановить сеть: повтор сохраняет UUID.
   Для формы проверить ручной повтор после ошибки и редактирование данных между попытками.
6. Отдельно проверить «Да»/«Нет», закрытие диалога, переходы между страницами и reload.

Одного `CALL_CLICK_ALLOWED_ORIGINS` недостаточно для новой Medtaxi-схемы: локальный
`MEDTAXI_URL` должен направлять события/формы в локальную Medtaxi DB. Не меняйте
production `MEDTAXI_URL` ради отладки локального frontend.

В production рекомендуем `NEXT_PUBLIC_API_URL=/api` и same-origin Nginx proxy.
Next.js самостоятельно `/api/feedback` не реализует. Изменение публичной переменной
требует пересборки. `404 Cannot POST` означает проблему маршрута/версии backend;
`403` — проверку Origin; `(failed)` — сетевой сбой, CORS либо блокировщик.

Диагностика в консоли: `[analytics]`, уровень Info для подтверждений.
`kind: "invalid_response"` — HTTP 2xx без корректного acknowledgement;
`"http"` — отказ API; `"network_or_cors"` — браузер не предоставил HTTP-ответ.
Телефон и полный payload не логируются. Серверная диагностика доставки и CLI
описаны в README `conditioners-server`; не используйте полные заявки как обычный лог.

## Проверки

```bash
yarn test:tracking
yarn test:call-feedback
yarn test
```

`tests/analyticsQueue.test.mjs` проверяет восстановление очереди, backoff, срок/лимит,
неверные подтверждения, независимость Метрики и UUID при разном порядке listeners.
`tests/CallFeedbackForm.test.mjs` проверяет повтор с прежним requestId, новый ID после
редактирования, сохранение полей при неверном acknowledgement и явные исходы звонка.
Все автоматические транспортные тесты используют подменённый HTTP, без реальных заявок.
